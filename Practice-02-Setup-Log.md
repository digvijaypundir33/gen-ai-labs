## Lessons carried over from Practice 01

Things that cost time last round and are being handled differently from the start:

- **Scoped IAM user needs delete permissions.** Practice 01's `ai-assistant-project-user` could
  create resources but not delete them — no `iam:Delete*`/`iam:Detach*`, and no DynamoDB
  permissions at all — so most of the teardown had to be re-run under the admin profile. This
  project's user gets `Delete*`/`Detach*` in its policy from day one.
- **Console-created resources create hidden dependencies.** The Step Functions console
  auto-generated an execution role with three extra managed policies that all had to be detached
  (and deleted, since they were customer-managed) before the role would delete. Anything the
  console auto-creates gets logged here explicitly, not assumed.
- **AppConfig has deletion protection.** Deleting an environment/application with recent activity
  is blocked at the account level; the console was the fastest way through it. Not expected to
  recur here since this project doesn't use AppConfig, but the general lesson holds — some
  services refuse deletion for reasons that aren't permissions.
- **S3 triggers aren't event-source mappings.** `aws lambda create-event-source-mapping` does not
  work for S3; S3 → Lambda is configured as a bucket notification, from the S3 side.

## Final teardown

When the project is done, work through the delete column above, roughly bottom to top
(newest/most-dependent resources first), then double-check in the console that S3, Lambda,
DynamoDB, API Gateway, Step Functions, Bedrock (Knowledge Bases + S3 Vectors), OpenSearch, and
IAM are all actually clear.

Two extra checks specific to this project, since RAG leaves data behind in more places than
Practice 01 did:

- **Empty the S3 buckets before deleting them** — a non-empty bucket refuses to delete, and
  versioned buckets need their versions purged too.
- **Delete the Knowledge Base *and* its underlying vector store.** Deleting the KB does not
  necessarily remove the vector index behind it; confirm the S3 Vectors bucket/index is gone
  separately.

Nothing here uses CloudFormation, so there's no single stack delete that sweeps everything.
